# 給教授的 Demo 腳本（約 8 分鐘）

## 事前準備（demo 前 5 分鐘）

```bash

# 2. 等 console 顯示「就緒」後，開瀏覽器 http://127.0.0.1:8000
# 3. 先跑一次台北→基隆路線暖機（預設模式下第一次會載局部圖）
# 4. 開好三個分頁：地圖 UI、gcn/results/ 圖表資料夾、報告網頁
```

## 第一幕：預測即時生效（3 分鐘）——對應計畫書 p.7–8 實驗 + 增量更新思想

> 台詞：「這是計畫書實驗章節的落地：T-GCN 用真實高公局資料預測 30 分鐘後的車速，
> 而且事件一產生就即時增量更新路網成本，不用全圖重算。」

1. 地圖上設台北車站 → 基隆，查路線 → 記下時間（**21.2 分**）
2. 觸發預測（重播工作日早上 8 點尖峰）：
   ```bash
   curl -X POST "http://127.0.0.1:8000/predict/run?at_index=4992"
   curl http://127.0.0.1:8000/predict/status   # 看 incremental_apply_ms
   ```
3. **指給教授看 status 裡的數字**：26 個預測壅塞、605 條邊、**1.35 秒增量套用**
   （對比：全圖 recompute 要 15–20 秒——這就是計畫書「增量 vs 全圖」的系統版）
4. 地圖重新整理 → 出現**紫色虛線圓**（預測壅塞，跟即時/手動事件視覺區隔）
5. 同一起終點再查 → 路線**立刻改變**（balanced：21.2 → 22.9 分改道；
   說明：壅塞折進時間項，所有模式都反應，這是我們對成本模型的改進）
6. 清除展示可逆性：
   ```bash
   curl -X DELETE http://127.0.0.1:8000/predict/events
   curl -X POST http://127.0.0.1:8000/dynamic/recompute -H "Content-Type: application/json" -d '{"mode":"balanced"}'
   ```
   再查路線 → 精確回到 21.2 分

## 教授可能的提問與答法

- **「訓練資料哪來的？」** 高公局 TDCS M05A，國道一號 148 個門架路段 × 21 天，
  5 分鐘粒度，各車種流量加權。超參數完全照計畫書 p.8（hidden 64、lr 0.001、Adam、50 epochs）。
- **「增量更新怎麼保證正確？」** 與全圖重算逐一比對，L1 誤差 < 1e-5；
  系統層的清除還原也驗證精確回到基準。
- **「為什麼不用 PyTorch Geometric？」** 計畫書要控制乘法順序與傳播流程，
  自己實作 Â·(X·W) 才能做 p.5–6 的實驗；也順便驗證了正確性（Pubmed 79.8% 達文獻水準）。
- **「硬體部分呢？」** DDA/DFA 屬 Verilog 範圍，本學期以軟體模擬對應
  （直接相依索引=DDMU 的軟體版），列為未來工作。
- **「跟你原本的導航系統什麼關係？」** 原系統是反應式（塞了才繞），
  整合後是預測式（會塞先繞）；預測事件走獨立的 source，原機制零修改。
